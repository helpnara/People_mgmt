# 소셜 네트워크 분석(SNA) 지표 도입 검토

- 대상 문서: 느린 인연 요구사항 정의서 v0.3
- 검토 요청: SNA 기법을 적용해 사람별 지표를 제공하는 기능 추가
- 반영: [requirements-v0.5.md](requirements-v0.5.md) · ADR-0003(N:M) · ADR-0004(점수화하지 않음) — 이 문서의 현재 모델은 2026-10-17 검토 당시의 것
- 결론 요약: **도입 가능하되, 세 가지 조건이 붙는다.** (1) 제품 원칙과의 충돌을 "사람 점수화"가 아니라 "관계 상태와 내 네트워크의 모양"으로 재정의해 해소해야 한다. (2) 현재 데이터 모델(사람 1 : 기록 N)은 별 모양 그래프라서 구조 지표가 전부 무의미하다. 기록에 여러 참여자를 허용하는 스키마 변경이 선행되어야 하며, 지금 반영하는 것이 가장 싸다. (3) 지표는 이인(나와 그 사람) 지표를 먼저, 구조(사람 간 연결) 지표를 나중에 단계적으로 넣는다.

## 1. 제품 원칙과의 충돌

v0.3 13절은 다음과 같이 선언한다.

> 느린 인연은 사람을 평가하거나 네트워크를 점수화하는 앱이 아니다.

"사람별로 지표화"는 이 문장과 정면으로 부딪힌다. 둘 중 하나를 바꿔야 하며, 원칙을 버리는 쪽보다 **지표의 대상을 바꾸는 쪽**을 권장한다.

| 구분 | 지표가 말하는 것 | 예 | 원칙과의 관계 |
|---|---|---|---|
| 사람 점수화 (비권장) | 그 사람의 가치·중요도 | "영향력 점수 87점", "핵심 인맥 Top 10" | 충돌 |
| 관계 상태 (권장) | 나와 그 사람 사이의 상태 | "8개월째 기록 없음", "최근 1년 식사 3회·회의 12회" | 양립 |
| 내 네트워크의 모양 (권장) | 나의 인연 전체의 구조 | "직장·대학·동호회 3개 그룹", "두 그룹을 잇는 사람은 2명" | 양립 |

재정의하면 지표는 "이 사람이 얼마나 중요한가"가 아니라 "내가 이 인연을 어떻게 돌보고 있는가"에 답한다. 이는 1.4 성공 기준("어떤 시간을 함께했는가")의 자연스러운 확장이다.

재정의와 함께 지켜야 할 표현 원칙:

1. **단일 합성 점수를 기본 화면에 두지 않는다.** 점수 하나로 요약되는 순간 사용자는 사람을 줄 세우게 된다. 개별 지표를 각각 보여 준다.
2. **순위표를 기본 제공하지 않는다.** "오래 못 만난 인연" 같은 행동 유도형 보기는 허용하되, "가장 중요한 사람" 식의 순위는 두지 않는다.
3. **설명 가능해야 한다.** 모든 지표는 탭하면 어떤 기록이 근거인지 보여 준다.
4. **기록 편향을 고지한다.** 지표는 실제 관계가 아니라 "내가 기록한 범위"를 반영한다. 안 적은 만남은 없는 만남으로 계산된다.
5. **중립적 언어를 쓴다.** "약한 관계"가 아니라 "최근 기록이 없음".

## 2. 데이터 모델 전제 조건

### 2.1 현재 모델의 한계

현재 모델은 `Person 1 ─ N Record`다. 그래프로 보면 **나(ego)를 중심으로 모든 사람이 나에게만 연결된 별(star) 모양**이고, 사람과 사람 사이의 선(edge)이 없다.

이 구조에서 고전적 SNA 중심성 지표를 계산하면 결과가 전부 같다.

| 지표 | 별 모양 그래프에서의 값 | 의미 |
|---|---|---|
| 연결 중심성 (degree) | 모든 사람 1 | 없음 |
| 매개 중심성 (betweenness) | 모든 사람 0 | 없음 |
| 근접 중심성 (closeness) | 모든 사람 동일 | 없음 |
| 고유벡터 / PageRank | 모든 사람 동일 | 없음 |
| 군집 계수 (clustering) | 정의 불가 | 없음 |
| 커뮤니티 탐지 | 커뮤니티 1개 | 없음 |

즉 **사람 간 연결 정보가 없으면 "구조 지표"는 하나도 계산할 수 없다.** 계산할 수 있는 것은 나와 그 사람 사이의 기록만으로 나오는 "이인 지표"뿐이다.

### 2.2 사람 간 연결을 만드는 세 가지 원천

| 원천 | 방법 | 신뢰도 | 입력 부담 | 필요한 스키마 변경 |
|---|---|---|---|---|
| **공동 참여** | 한 기록에 여러 사람을 참여자로 지정. 같은 기록에 함께 있으면 연결, 가중치는 공동 기록 수 | 높음 | 낮음 (선택 입력) | `Record ↔ Person` N:M |
| **소개 관계** | "이 사람을 누가 소개했는가" | 높음 | 낮음 | `Person.introducedBy: Person?` |
| **속성 공유** | 같은 소속·같은 태그면 약한 연결로 추정 | 낮음 (같은 회사라고 아는 사이는 아님) | 없음 | 없음 |

공동 참여가 핵심이다. "팀 회식", "3자 미팅", "프로젝트 킥오프"처럼 실제로 여러 사람이 함께한 기록이 사람 간 연결의 가장 정직한 근거다. 속성 공유는 보조로만 쓰고 기본은 끈다.

### 2.3 스키마 변경 제안

**(가) 기록 참여자 N:M** — 지금 반영 권장

- `Record.participants: [Person]` (1명 이상). 현재의 `Record.person`을 대체한다.
- UI: 기록 추가 화면에 "함께한 사람 추가" 선택 항목. 기본은 현재 사람 1명이므로 입력 흐름은 바뀌지 않는다.
- 타임라인: 참여자 각각의 타임라인에 같은 기록이 나타난다. 행에 "외 2명" 표시.
- 삭제 규칙 변경: 사람 삭제 시 그 사람이 **유일한 참여자**인 기록만 삭제하고, 다른 참여자가 있는 기록에서는 참여자 목록에서만 제거한다. 삭제 확인 문구에 "단독 기록 N건 삭제, 공동 기록 M건에서 제외"를 표시한다.
- 검색: 기록 필드 일치 시 참여자 전원이 결과에 나온다.
- 영향 절: 4.2.4, 4.3, 5.1 FR-006/009, 6.2, 6.5, 7.6, 9.1 AC-08.
- 지금 반영해야 하는 이유: 1:N에서 N:M으로의 마이그레이션은 관계 테이블 신설과 기존 데이터 이전이 필요해 이후 비용이 크다. 지금은 스키마 한 줄과 선택 입력 UI 하나로 끝난다.

**(나) 소개 관계** — 지금 반영 권장 (비용 매우 낮음)

- `Person.introducedBy: Person?` (선택). 알게 된 경로를 "소개"로 고르면 소개한 사람을 선택하는 필드가 나타난다.
- 사람 상세에 "OOO의 소개로" 표시, 소개한 사람 상세에 "소개한 인연 N명".
- 소개한 사람이 삭제되면 nil로 둔다(nullify).

**(다) 도움 방향** — P1

- `Record.helpDirection: gave / received / mutual` (기록 유형이 "도움"일 때만). 상호성 지표의 근거가 된다.

**(라) 지표 캐시** — 지표 도입 시

- 지표는 저장하지 않고 파생 계산한다. 다만 구조 지표는 계산 비용이 있으므로 `MetricsSnapshot { computedAt, perPerson: [UUID: PersonMetrics], network: NetworkMetrics }`를 메모리와 디스크에 캐시하고, 사람·기록 변경 시 무효화한다.

## 3. 지표 후보 평가

### 3.1 이인 지표 (나 ↔ 그 사람) — 스키마 변경 없이 가능

| 지표 | 정의 | 필요 데이터 | 가치 | 제안 |
|---|---|---|---|---|
| 기록 수 | 전체 / 최근 12개월 기록 건수 | 기록 | 높음 | P1 |
| 마지막 기록 경과 | 오늘 − 가장 최근 `occurredAt` | 기록 | 높음 | P1 |
| 인연 기간 | 처음 만난 날(없으면 첫 기록) ~ 마지막 기록 | 기록, firstMetDate | 중간 | P1 |
| 접촉 빈도 | 기록 수 ÷ 활성 개월 수 | 기록 | 중간 | P1 |
| 추세 | 최근 6개월 기록 수 vs 직전 6개월 (상승·유지·하락) | 기록 | 높음 | P1 |
| 유형 다양성 | 기록 유형 분포의 엔트로피 (식사·회의·도움이 섞일수록 높음). Granovetter의 다중성(multiplexity)에 해당 | 기록 유형 | 중간 | P1 |
| 규칙성 | 기록 간격의 변동계수 (정기적 만남 vs 몰아서) | 기록 | 낮음 | P2 |
| 상호성 | 도움 준 기록 vs 받은 기록 비율 | helpDirection | 중간 | P2 |
| 유대 강도 (합성) | 빈도·최근성·다양성·기간의 가중합 | 위 전부 | 논란 | 기본 화면 비표시. 정렬 기준으로만 선택 제공 |

이 묶음만으로도 "오래 못 만난 인연", "올해 새로 쌓인 인연", "식사만 하고 일은 안 해 본 사람" 같은 돌아보기가 가능하다. SNA 용어를 쓰지 않아도 되고 제품 원칙과도 충돌하지 않는다.

### 3.2 구조 지표 (사람 ↔ 사람) — N:M 참여자 필요

| 지표 | 정의 | 가치 | 제안 |
|---|---|---|---|
| 연결 수 | 내 네트워크 안에서 함께 기록된 다른 사람 수 | 중간 | P2 |
| 커뮤니티 | Louvain 또는 Label Propagation으로 사람들을 그룹으로 묶음. "직장", "대학", "프로젝트 A" 같은 집단이 자동으로 드러남 | 높음 | P2 |
| 매개 역할 | ego 네트워크 안 매개 중심성(Brandes). 서로 다른 그룹을 잇는 사람 = 나에게 다리 역할을 하는 사람 | 높음 | P2 |
| 가중 연결 강도 | 공동 기록 수로 가중한 엣지. 시각화와 커뮤니티 계산의 입력 | 중간 | P2 |
| 근접 중심성 | ego 네트워크에서는 모두 비슷하게 나옴 | 낮음 | 제외 |
| 고유벡터 / PageRank | 수백 명 규모 ego 네트워크에서는 연결 수와 거의 같은 순서. 설명도 어려움 | 낮음 | 제외 |
| 중개 역할 유형 (Gould-Fernandez) | 조정자·문지기·연락책 분류. 개인 앱에서 과함 | 낮음 | 제외 |

### 3.3 전체 네트워크 지표 (나의 인연 전체)

제품 원칙과 가장 잘 맞는 묶음이다. 평가 대상이 사람이 아니라 나 자신이기 때문이다.

| 지표 | 정의 | 제안 |
|---|---|---|
| 규모 | 등록 인원, 최근 12개월 기록이 있는 활성 인원 | P1 |
| 신규 인연 | 올해 처음 만난 사람 수 | P1 |
| 소홀한 인연 | 마지막 기록이 N개월 이상 지난 사람 수와 목록 | P1 |
| 구성 다양성 | 관계 유형·소속 분포 (엔트로피) | P2 |
| 그룹 수와 크기 | 커뮤니티 탐지 결과 | P2 |
| 밀도 | 실제 연결 수 ÷ 가능한 연결 수. 내 인연들이 서로 아는 정도 | P2 |
| 구조적 공백 (Burt의 constraint) | 내 인연들이 서로 모르는 정도. 낮을수록 다양한 집단에 걸쳐 있음 | P2 |
| 던바 계층 분포 | 접촉 빈도 기준 5 / 15 / 50 / 150명 층에 몇 명씩 있는지 | P2 (해석 주의 문구 필요) |

## 4. 구현 가능성 (기기 내, 서드파티 없이)

| 항목 | 판단 |
|---|---|
| 데이터 규모 | 사람 1,000명, 기록 10,000건이면 노드 1,000개, 엣지 수천 개. 매우 작은 그래프 |
| 이인 지표 | 기록 1회 순회로 전부 계산. 밀리초 단위. 상세 화면 진입 시 즉시 계산 가능 |
| 매개 중심성 | Brandes 알고리즘 O(V·E). 1,000 × 5,000 = 5백만 연산 수준. 백그라운드에서 1초 이내 |
| 커뮤니티 탐지 | Label Propagation은 구현 50줄 내외, Louvain은 200줄 내외. 둘 다 Swift로 직접 작성 가능. 결정론적 결과를 위해 시드 고정 |
| 외부 의존성 | 불필요. 8.1 "Apple 프레임워크만" 원칙 유지 가능 |
| 계산 시점 | 이인 지표는 즉시 계산. 구조 지표는 앱 실행 후와 데이터 변경 후 백그라운드 재계산, 스냅샷 캐시 |
| 시각화 | SwiftUI Canvas로 force-directed 그래프 그리기 가능. 노드 100개 이하에서 의미 있고 그 이상은 커뮤니티별 묶음 보기가 낫다. P2 |
| 테스트 | 지표 계산은 순수 함수로 분리해 알려진 소형 그래프(삼각형, 별, 두 덩어리)로 단위 테스트 |

### 4.1 주의할 점

- **희소 데이터.** 기록 3건인 사람의 "추세"나 "규칙성"은 잡음이다. 지표마다 최소 기록 수 임계값을 두고 미만이면 "기록이 더 쌓이면 표시됩니다"로 대체한다.
- **기록 편향.** 사용자가 적는 사람만 지표가 좋아진다. 모든 지표 화면에 "내가 기록한 범위 기준" 문구를 둔다.
- **시간 창.** 10년치 기록에서 "활성"의 기준은 12개월, "소홀"의 기준은 6개월처럼 기본값을 두고 설정에서 바꿀 수 있게 한다.
- **커뮤니티 이름.** 알고리즘은 그룹을 번호로만 내놓는다. 그룹 안 다수의 소속·태그로 이름을 제안하고 사용자가 고칠 수 있게 한다.
- **개인정보.** 모두 기기 내 계산이므로 추가 위험은 없다. 내보내기에 지표를 포함할지는 별도 결정.

## 5. 요구사항 반영 제안

| 우선순위 | 항목 | 내용 |
|---|---|---|
| **P0 (지금, 스키마만)** | 기록 참여자 N:M | `Record.participants`, "함께한 사람 추가" 선택 UI, 삭제 규칙 변경 |
