# 느린 인연 요구사항 정의서 v0.1 검토 의견서

- 검토 대상: 느린 인연 요구사항 정의서 v0.1 (초기 요구사항 초안)
- 검토 목적: iPhone 앱 개발 착수 전 요구사항의 일관성·충분성·누락 여부 점검
- 결과물: 본 의견서 + 검토 반영본 `requirements-v0.2.md`

---

## 1. 총평

v0.1은 제품 비전, 포함/제외 범위, 우선순위(P0/P1/P2), 데이터 모델 초안, 수용 기준까지 갖춘 좋은 초안이다. "사람을 중심 객체로 두고 인연의 역사를 기록한다"는 방향과 "복잡한 CRM을 만들지 않는다"는 절제가 문서 전체에서 일관되게 유지된다.

다만 그대로 개발에 착수하면 구현자가 임의로 해석해야 하는 지점이 많다. 크게 세 묶음이다.

1. **문서 내부의 모순 9건**: 같은 기능이 어떤 절에서는 P0 범위이고 다른 절에서는 P1이거나, 데이터 모델의 필수 조건과 사용성 원칙이 충돌한다. 이 항목은 결정이 필요하다.
2. **명세 부족 18건**: 기술 스택, 정렬 규칙, 검색 동작, 입력 검증, 삭제 범위, 성능·접근성 기준처럼 구현 시 반드시 정해야 하는데 문서에 없는 내용이다.
3. **보완 권고 12건**: 개인용 관계 기록 앱이라는 특성상 넣는 편이 좋은 항목(앱 잠금, 연락 수단 메모, 마지막 기록일 등)과 향후 확장을 위해 지금 예약해 두어야 하는 설계 사항이다.

검토 결과는 모두 v0.2에 반영했다. 사용자 확인이 필요한 결정 사항은 4절에 모았고, v0.2는 각 항목의 **권장안**을 채택한 상태로 작성했다. 다른 선택을 원하면 해당 부분만 되돌리면 된다.

## 2. 검토 관점과 표기

| 표기 | 의미 |
|---|---|
| 🔴 모순 | 문서 안에서 서로 다른 해석이 가능하다. 결정이 필요하다. |
| 🟡 명세 부족 | 구현자가 임의로 정해야 한다. 명세를 보강해야 한다. |
| 🟢 보완 권고 | 없어도 POC는 가능하지만 넣는 편이 제품 목적에 맞다. |

검토 관점: (1) 문서 내부 일관성, (2) 구현 가능성과 명세 충분성, (3) 누락 기능, (4) iPhone 플랫폼 특성, (5) 개인정보 보호, (6) 검증 가능성(수용 기준).

## 3. 상세 검토 결과

### 3.1 🔴 내부 모순 (결정 필요)

**R-01. 태그의 우선순위가 절마다 다르다.**
- 1.3 핵심 가치 3 "검색과 태그를 통해 재발견", 2.2 포함 범위 "키워드 검색 및 태그", 4.1 화면 구성에 태그 입력 항목 존재.
- 반면 FR-011 태그는 P1, 9절 수용 기준에 태그 없음, 10절 4단계 "구현 여건에 따라 태그 기능 추가".
- 영향: 태그가 핵심 가치에 포함되어 있는데 POC에서 빠질 수 있다. 태그 없이는 "재발견" 가치를 검증할 수 없다.
- 권장: **태그 입력·표시·태그 검색을 P0로 승격**한다. 태그 자동완성, 이름 변경, 병합 같은 관리 기능은 P1로 둔다. 자유 문자열 배열로 구현하면 P0 비용이 작다.

**R-02. 기록 날짜가 필수인데 사용성 원칙은 날짜 미입력을 허용한다.**
- 6.2 `RelationshipRecord.occurredAt` 필수. 7절 5항 "날짜를 모르는 경우 억지로 입력하지 않아도 된다."
- 영향: 기록 추가 화면에서 날짜를 비울 수 있는지 구현자가 판단해야 하고, 비운다면 타임라인 정렬 규칙이 없다.
- 권장: 두 개념을 분리한다. **기록(Record)의 날짜는 필수이되 기본값을 오늘로** 하여 입력 부담을 없앤다. 날짜 미입력 허용은 **사람(Person)의 처음 만난 날짜**에만 적용한다. "2019년쯤"처럼 대략적인 날짜는 P1에서 `datePrecision`(일/월/년) 필드로 지원한다.

**R-03. "첫 만남" 개념이 두 곳에 있다.**
- Person에 `firstMetDate`, `firstNote`가 있고, 6.3 기록 유형에도 "첫 만남"이 있다.
- 영향: 사용자가 첫 만남을 사람 정보에 쓸지 기록으로 쓸지 혼란스럽고, 둘 다 쓰면 타임라인에 중복된다. 검색·내보내기에서도 두 경로를 처리해야 한다.
- 권장: **첫 인연은 Person의 속성으로 단일화**하고 기록 유형에서 "첫 만남"을 제거한다. 타임라인에서는 첫 인연을 가장 오래된 항목 자리에 "시작점"으로 파생 표시한다(저장하지 않음). 수정은 사람 정보 수정 화면에서 한다. 이렇게 하면 "이 사람을 어떻게 알게 되었는가"라는 질문에 답하는 정보가 항상 한 곳에 있다.

**R-04. 사진이 화면 구성과 데이터 모델에는 있으나 FR-012는 P1이다.**
- 권장: 모델 필드 `photoReference`는 지금 둔다(스키마 변경 최소화). 사진 선택·표시 UI는 P1로 명시하고 4.1 화면 구성에 "(P1)"을 표기한다.

**R-05. 기록 추가 화면에 "관련 프로젝트" 항목이 있으나 FR-016 프로젝트 연결은 P2다.**
- 권장: POC 화면에서 제거한다. 대신 데이터 모델에 외부 참조를 위한 확장 지점(6.5절)을 설계 메모로 남긴다. 지금 스키마에 필드를 넣지는 않는다.

**R-06. 검색 대상이 세 곳에서 다르게 쓰여 있다.**
- FR-010 "이름 및 기록의 주요 텍스트", 4.1 검색 결과 "이름, 소속, 메모, 태그", 3.2 시나리오 C "이름 또는 키워드".
- 권장: 검색 대상 필드를 표로 확정한다(v0.2 5.3절). Person: 이름, 소속, 직무, 관계 유형, 알게 된 경로, 첫 인연 메모, 태그. Record: 제목, 메모, 장소, 태그. 결과 단위는 사람이며 어떤 필드가 일치했는지 근거를 함께 보여준다.

**R-07. 기록 제목이 필수인데 "빠른 기록" 원칙과 충돌한다.**
- "점심 먹으며 이직 고민 들음" 같은 짧은 기록에 제목까지 요구하면 입력이 두 번이 된다.
- 권장: **제목과 메모 중 하나만 있으면 저장 가능**하게 한다. 제목이 비어 있으면 "유형 · 날짜" 또는 메모 첫 줄로 표시명을 만든다.

**R-08. FR-014 내보내기와 FR-018 백업·복원이 P1인데 11.2 "추가 기능 후보"에 다시 나온다.**
- 권장: 11.2에서 제거한다. 후보 목록은 FR 표에 없는 항목만 남긴다.

**R-09. 홈 화면 "최근 기록 또는 최근 등록한 사람(선택 기능)"에 우선순위가 없다.**
- 권장: P1(FR-028)로 번호를 부여한다.

### 3.2 🟡 명세 부족 (보강 필요)

**S-01. 기술 스택과 최소 iOS 버전이 없다.**
- 개인용 POC이고 데이터 계층 분리를 요구하므로 **SwiftUI + SwiftData, iOS 17 이상**을 권장한다. SwiftData는 iOS 17부터 쓸 수 있고 CloudKit 동기화로 확장하기 쉽다. 복잡한 쿼리나 iOS 16 지원이 필요하면 Core Data가 대안이다. 결정 D-1.

**S-02. 기록 상세 화면이 없다.**
- 타임라인에서 기록을 탭했을 때 무엇이 보이는지 정의되어 있지 않다. 긴 메모(8.4 "긴 메모를 읽기 편해야 한다")를 읽으려면 상세 화면이 필요하다. v0.2 4.1에 "기록 상세" 화면을 추가했다.

**S-03. 사람 목록의 정렬·그룹 기준이 없다.**
- 기본 정렬은 이름 가나다순(로케일 기준 비교), 보조 정보로 소속·관계 유형을 표시한다. 최근 기록순 정렬은 P1.

**S-04. 타임라인의 정렬 규칙이 "날짜순"뿐이다.**
- 최신순을 기본으로 하고, 같은 날짜는 생성 시각 역순으로 정한다. 첫 인연 항목은 항상 맨 아래(가장 오래된 자리)에 둔다.

**S-05. 삭제 범위가 정의되어 있지 않다.**
- 사람 삭제 시 연결된 기록 전체가 함께 삭제됨(cascade)을 명시하고, 확인 문구에 기록 건수를 표시한다. 7절 8항 "삭제 범위를 명확하게"를 구체화한 것이다.

**S-06. 입력 검증 규칙이 없다.**
- 공백만 입력한 이름, 길이 제한, 태그 정규화(앞뒤 공백 제거, `#` 제거, 대소문자 무시 중복 제거), 최대 태그 수 등을 표로 정의했다(v0.2 7.2절).

**S-07. 관계 유형과 알게 된 경로의 선택지 목록과 직접 입력 가능 여부가 없다.**
- 시나리오 A에는 "선택하거나 입력한다"고 되어 있으나 목록이 없다. 초기 선택지 목록과 "직접 입력" 허용을 명시했다(v0.2 6.3절).

**S-08. 입력 도중 이탈할 때의 동작이 없다.**
- 변경 사항이 있는 상태에서 취소하거나 화면을 내리면 "변경 사항을 버릴지" 확인한다. 실수로 긴 메모를 잃는 것을 막는다.

**S-09. 저장 실패 시나리오가 추상적이다.**
- 8.2 "실패 사실과 가능한 조치를 안내"를 구체화했다. 저장 실패 시 입력 내용을 화면에 유지하고 재시도를 제공하며, 저장 공간 부족이 원인일 수 있음을 안내한다.

**S-10. 검색 동작이 정의되어 있지 않다.**
- 부분 일치 여부, 대소문자 처리, 한글 정규화(NFC), 여러 단어 입력 시 AND/OR, 실시간 검색 여부, 결과 표시 형식을 정했다. 초성 검색은 P2.

**S-11. 수용 기준이 측정 가능한 형태가 아니고 항목이 빠져 있다.**
- 태그, 중복 이름 안내, 입력 검증, 미저장 변경 보호, 동일 날짜 정렬, 삭제 범위 안내, 다이나믹 타입이 수용 기준에 없다. Given/When/Then 형식으로 다시 썼다(v0.2 9절).

**S-12. 성능 목표가 없다.**
- 개인용이라도 수년간 쓰면 기록이 수천 건이 된다. 사람 1,000명·기록 10,000건을 기준 데이터 규모로 정하고 목록·검색·저장 응답 시간 목표를 넣었다.

**S-13. 접근성 기준이 추상적이다.**
- Dynamic Type 지원 범위, VoiceOver 레이블 규칙, 색상 대비, 최소 터치 영역, 색상에만 의존하지 않는 구분 등 iOS 기준으로 구체화했다.

**S-14. "기기 내 저장"과 iOS 기기 백업의 관계가 없다.**
- 앱 데이터는 사용자가 iCloud 백업이나 컴퓨터 백업을 켜 두었다면 자동으로 포함된다. 이는 앱이 클라우드 동기화를 하는 것과 다르지만, 개인정보 절에서 "데이터가 어디에 존재할 수 있는가"를 정직하게 적어야 한다. v0.2 8.3절에 명시했다.

**S-15. 스키마 버전과 마이그레이션 전략이 없다.**
- 데이터 계층 분리를 요구하면서 스키마 진화 방법이 없다. 첫 버전부터 스키마에 버전을 부여하고 마이그레이션 경로를 유지하도록 했다.

**S-16. 언어·로케일 정책이 없다.**
- 한국어 UI 전용으로 정하되, 문자열은 String Catalog로 관리해 추후 영어 추가가 가능하게 했다. 날짜 표시는 기기 로케일을 따른다.

**S-17. 테스트 전략이 수동 확인 위주다.**
- 10절 5단계는 모두 수동 테스트다. 저장소 CRUD, 검색 일치, 태그 정규화, 정렬, 삭제 cascade는 단위 테스트로 고정하고, 대표 시나리오 A/B/C는 UI 테스트로 자동화하도록 했다(v0.2 11절).

**S-18. 배포 방식이 없다.**
- 개인용이라도 설치 방법은 정해야 한다. 무료 Apple 계정으로 Xcode에서 직접 설치하면 7일마다 재설치가 필요해 파일럿에 부적합하다. Apple Developer Program 가입 후 TestFlight 배포(빌드당 90일)를 권장한다. 결정 D-6.

### 3.3 🟢 보완 권고

**G-01. 앱 잠금(Face ID / Touch ID / 기기 암호).** 사람에 대한 개인적인 메모가 쌓이는 앱이다. 기기 잠금만으로 충분하다고 볼 수도 있으나, 다른 사람에게 폰을 건네는 상황이 잦다. P1 권장. 기본값 꺼짐.

**G-02. 연락 수단 메모 필드.** 앱의 중심은 전화번호가 아니지만, 전화·이메일을 전혀 둘 곳이 없으면 결국 주소록을 왕복하게 된다. 구조화된 전화·이메일 필드 대신 **자유 텍스트 1개(`contactNote`)** 를 P1로 두면 개인정보 최소화 원칙과도 맞는다.

**G-03. 마지막 기록일 파생 표시.** 사람 목록에 "마지막 기록 3개월 전"을 보여 주면 11.2의 "마지막 만남 기준 보기"를 가장 싸게 실현한다. 별도 저장 없이 기록에서 계산한다. P1.

**G-04. 기록 유형별 아이콘.** 8.4 "날짜, 유형, 태그가 시각적으로 구분"을 구현하려면 유형별 SF Symbol 매핑이 필요하다. v0.2 6.4절에 포함했다.

**G-05. 설정 화면 최소 구성.** 앱 정보, 개인정보 안내, 전체 데이터 삭제, (P1) 앱 잠금 토글, 백업 파일 내보내기·가져오기. P1.

**G-06. 삭제 실행취소.** 하드 삭제 + 확인 대화상자가 POC 기본이지만, 실수 삭제 복구는 개인 기록 앱에서 체감 가치가 크다. 삭제 직후 수 초간 "실행취소" 제공을 P1로 둔다.

**G-07. 느린 시리즈 연동을 위한 식별자 예약.** 모든 엔터티 ID를 UUID로 하고, 외부 참조 구조(앱 식별자 + 엔터티 종류 + 외부 ID)를 설계 메모로 남긴다. 지금 필드를 추가하지는 않는다.

**G-08. 용어집.** Person/사람, Record/기록, 관계 유형, 알게 된 경로, 첫 인연, 태그의 정의와 표기를 통일한다. v0.2 0.3절.

**G-09. 다크 모드.** SwiftUI 기본 지원이지만 명시적으로 요구사항에 넣어 테스트 항목으로 만든다.

**G-10. 저장 파일 보호.** 가능한 경우 iOS 데이터 보호 클래스 "완전 보호"를 적용한다. 백그라운드 작업이 없는 앱이므로 제약이 적다.

**G-11. 별명·호칭 필드.** "김 부장님", "민수 형"처럼 실제로 부르는 이름으로 검색하는 경우가 많다. P1 선택 필드.

**G-12. 시나리오 추가.** v0.1 시나리오는 등록·기록·검색만 다룬다. 수정·삭제, 날짜를 모를 때, 동명이인 등록 시나리오를 추가했다.
