# 관계도의 커뮤니티 탐지 검토

> 사용자 (2026-10-18): *관계도 그릴 때 community detection algorithm 중 louvain method와 같은 전문성 있게 표현이 가능한지 검토해줘. 필요한 인자가 어떤 것들이 있고 입력 정보를 어떻게 개선할 수 있을지도 고민해보자.*

**결론.** 가능하다. 기기 안에서 서드파티 없이 돈다 — 5,000명 · 수만 선에서도 1초 안쪽. **막히는 것은 알고리즘이 아니라 입력이다.** 지금 자료로 돌리면 대부분 혼자 떨어진 사람이거나, 같은 소속 선 때문에 "회사별 묶음" 이 그대로 나온다(되풀이). 그래서 순서는 **① 입력을 늘리는 장치 → ② 탐지(Louvain + 연결 쪼개기) → ③ 그룹 이름 · 표현** 이다.

## 1. 지금 관계도의 입력 — 무엇이 선이 되는가

| 원천 | 지금 | 탐지에 쓸 만한가 |
|---|---|---|
| 함께한 기록(공동 참여) | 진한 선, 굵기 = 함께한 기록 수 | **가장 좋다.** 실제로 함께한 일. 다만 지금은 대부분 기록이 한 사람짜리라 선이 적다 |
| 소개 관계 | 진한 선 | 좋다. 다만 한 사람당 하나뿐이라 별 모양만 만든다 |
| 같은 소속 | 옅은 점선(끄고 켬) | **탐지에는 넣지 않는 편이 낫다.** 넣으면 결과가 "소속별 묶음" 과 같아져 새로 알려 주는 것이 없다. 그룹 이름을 지을 때 쓴다 |
| 나 | 가운데 고정, 선 없음 | 탐지에서 **반드시 뺀다.** 모두가 나와 이어져 있어 넣으면 한 덩어리가 된다 (ego 제외 — 요구사항 5.5) |

## 2. 알고리즘 — 무엇을 쓸까

| 후보 | 장점 | 단점 | 판단 |
|---|---|---|---|
| **Louvain** (모듈성 최대화) | 가장 널리 쓰이고 설명이 쉽다. 가중 그래프 그대로. 구현 200줄 안팎 | 결과 그룹이 **끊어져 있을 수 있다**(한 그룹 안에서 서로 이어지지 않은 조각). 노드 차례에 따라 결과가 조금 달라진다 | 쓴다 + 아래 두 보완 |
| Leiden | Louvain 의 끊긴 그룹 문제를 고친 후속. 품질이 더 좋다 | 구현이 두 배쯤. 정답표(파이썬 대조)를 맞추기 더 어렵다 | 지금은 과하다. 자료가 수천 명이 되면 다시 본다 |
| Label Propagation | 50줄. 빠르다 | 결과가 흔들린다(같은 자료에서도 차례에 따라 다른 답). 설명이 어렵다 | 빼다 |

**보완 둘.**
1. **연결 쪼개기** — Louvain 이 낸 그룹마다 안쪽 선만으로 연결 조각을 찾아, 끊긴 조각은 다른 그룹으로 나눈다. Leiden 이 보장하는 성질을 값싸게 얻는다.
2. **고정 차례** — 노드를 이름 열쇠 · uuid 순으로 돌리고 난수를 쓰지 않는다. 같은 자료면 늘 같은 그룹 → 파이썬 정답표로 대조할 수 있다 (`Tools/golden`).

## 3. 필요한 인자

| 인자 | 뜻 | 기본값 제안 | 사용자에게 보일까 |
|---|---|---|---|
| **선 가중치** | 함께한 기록 1건 = 1, 소개 = 1, 같은 소속 = 0(탐지 제외) | 왼쪽 | 아니요 |
| **시간 감쇠** | 오래된 함께한 기록일수록 가볍게. 반감기 | 2년 (2년 전 기록은 0.5) | 아니요 |
| **해상도 γ** | 클수록 그룹이 잘게 쪼개진다. 모듈성 식의 계수 | 1.0 | 선택: "크게 묶기 / 잘게 나누기" 세 단계 |
| **최소 개선량 ε** | 모듈성이 이만큼도 안 오르면 멈춘다 | 1e-7 | 아니요 |
| **최소 그룹 크기** | 이보다 작은 그룹은 그룹으로 보이지 않고 "흩어진 사람" 으로 | 3명 | 아니요 |
| **보여 줄 문턱** | 진한 선이 이보다 적거나 모듈성 Q 가 낮으면 그룹을 그리지 않고 "기록이 더 쌓이면 그룹이 보입니다" | 진한 선 20개 · Q ≥ 0.3 | 아니요 (원칙 4) |
| 반복 상한 | 층(레벨) 수 · 한 층의 돌기 횟수 상한 — 무한 반복 막기 | 10층 · 50번 | 아니요 |

## 4. 입력을 늘리는 방법 — 이것이 품질을 정한다

자아 중심 네트워크 연구(ego-network survey)는 보통 "이 사람과 저 사람은 서로 아는가" 를 **직접 묻는다**. 기록만으로 모으기에는 너무 느리다.

| 장치 | 내용 | 효과 | 비용 · 위험 |
|---|---|---|---|
| **A. 아는 사이 잇기** | 사람 편집에 `이 사람과 아는 사람` 고르기(여러 명). 기록 없이 사람 ↔ 사람 선을 만든다 | **가장 크다.** 하루 10명 입력하며 바로 선이 생긴다 | 스키마 4판(사람 ↔ 사람 다대다 하나). 고르기 화면 하나 |
| **B. 모임 · 그룹** | `동호회 A` · `프로젝트 B` 처럼 모임을 만들고 사람을 넣는다. 같은 모임 = 선 | 크다. 모임 이름이 곧 그룹 이름 후보 | 새 객체(모임). 화면 둘. 태그와 겹칠 수 있다 |
| C. 기록의 함께한 사람 늘리기 | 기록 추가 때 같은 소속 · 최근 함께한 사람을 위에 띄워 고르기 쉽게 | 중간. 지금 구조 그대로 | 화면만 |
| D. 시간 감쇠 | 오래된 함께함은 가볍게 (3절) | 지금의 묶음이 드러난다 | 없음 |
| E. 소속 이력 | 지금은 소속 하나. 전 직장 · 학교를 여럿 | 이름 짓기가 좋아진다 | 스키마 변경 |
| ✗ 친밀도 점수 입력 | 사람마다 1~5 점 | — | **넣지 않는다** — 사람을 점수화한다 (ADR-0004) |

**추천: A 를 먼저.** 탐지의 입력이 바로 늘고, 연구에서 쓰는 방식과 같고, 점수화 없이 "서로 아는가" 만 묻는다. B 는 태그로 상당 부분 대신할 수 있어 나중에 본다.

## 5. 표현 — 그룹을 어떻게 보여 줄까

- **색을 그룹마다 나누지 않는다.** 범주 색은 셋을 넘으면 구분이 안 된다(시각화 기준 · 빌드 9 관계도와 같은 판단). 대신 그룹마다 **옅은 둥근 영역(외곽선)** 과 **그룹 이름 글자**를 그리고, 그룹 칩을 고르면 그 그룹만 진하게.
- **그룹 이름 제안** — 그룹 안에서 가장 많은 소속 → 태그 → 알게 된 경로 순으로. 예: `청림소프트 · 7명`. 사용자가 고칠 수 있게(FR-047).
- **이름이 바뀌지 않게** — 자료가 바뀌면 그룹 번호가 바뀐다. 새 그룹을 옛 그룹과 구성원 겹침(Jaccard)으로 짝지어, 겹침이 절반 넘으면 사용자가 붙인 이름을 이어받는다. 이름을 저장하려면 작은 객체(그룹 이름) 하나가 필요하다.
- **점수 · 순위는 여전히 없다.** 모듈성 Q 같은 숫자는 화면에 내지 않는다 — 보여 줄지 말지의 문턱으로만 쓴다. 매개 중심성(그룹을 잇는 사람)은 요구사항대로 수치 없이 "두 그룹을 잇는 사람" 표시만, 그것도 다음 단계.
- 특성 · 돌아보기 화면에 `그룹` 분포를 더한다 — 그룹을 누르면 그 사람들(근거).

## 5-1. 시점에 따라 변하는 관계 모양 (사용자 제안 · 2026-10-18)

> 사용자: *계산 시점에 따라서 관계 모양이 변할 것 같거든. 이런 부분도 반영되면 좋을 것 같아.*

맞다. 같은 사람들이라도 3년 전의 묶음(전 직장 · 대학원)과 지금의 묶음(새 팀 · 동호회)은 다르다. 기록마다 날짜(`occurredAt`)가 있어 **지난 시점의 관계도를 되살릴 수 있다.** 연구에서는 시간 네트워크(temporal network) · 커뮤니티 변화 추적이라 부른다.

**어떻게 자르나 — 시점 t 의 관계도**

| 인자 | 뜻 | 기본값 제안 |
|---|---|---|
| **창 길이** | 시점 t 에서 얼마 전까지의 함께함을 볼지 | 12개월 (t 이전 1년) |
| **걸음** | 시점을 얼마 간격으로 옮길지 | 3개월 (분기) |
| 창 안의 감쇠 | 창 안에서도 t 에 가까울수록 무겁게 | 반감기 6개월 |
| 사람이 그 시점에 있었나 | 처음 만난 날 ≤ t, 없으면 첫 기록일 ≤ t. 둘 다 없으면 그 시점에 **그리지 않는다** (언제 알았는지 모른다) | — |
| 조각 문턱 | 그 시점의 진한 선이 적으면 그룹 대신 "이 시기는 기록이 적습니다" | 진한 선 10개 |

- **소개 관계에는 날짜가 없다** → 소개받은 사람의 처음 만난 날을 소개 시점으로 쓴다.
- **아는 사이 잇기(4절 A)** 를 넣는다면 `언제부터 알았나` 를 선택 칸으로 둔다 (비우면 두 사람 중 늦게 만난 날).
- **소속에는 날짜가 없다** — 지금 소속만 안다. 지난 시점에는 소속 선 · 소속 이름 짓기를 쓰지 않는다 (틀린 과거를 그리지 않게).

**그룹이 어떻게 변했나 — 이어 붙이기**

시점마다 그룹을 따로 찾고, 바로 앞 시점의 그룹과 **구성원 겹침(Jaccard)** 으로 짝짓는다. 짝이 이어지면 같은 그룹(같은 이름 · 같은 자리)이다. 짝짓기 결과로 변화를 **중립적인 말**로 말한다 (원칙 5):

| 변화 | 판정 | 보여 줄 말 |
|---|---|---|
| 새로 생김 | 앞 시점에 짝이 없다 | `새로 생긴 묶음` |
| 커짐 · 작아짐 | 짝은 있고 사람 수가 30% 넘게 변했다 | `사람이 늘었습니다` · `줄었습니다` |
| 합쳐짐 | 앞 시점의 두 그룹이 한 그룹의 짝 | `두 묶음이 이어졌습니다` |
| 나뉨 | 앞 시점의 한 그룹이 두 그룹의 짝 | `한 묶음이 나뉘었습니다` |
| 흩어짐 | 다음 시점에 짝이 없다 | `최근 기록 없음` (사라졌다 · 끊겼다 같은 말은 쓰지 않는다) |

**보여 주기**

- 관계도 아래 **시점 막대**: `2023년 1분기 … 지금`. 끌면 그 시점의 관계도로 바뀐다. 재생 단추로 분기마다 넘긴다.
- **자리가 튀지 않게** — 다음 시점의 배치를 앞 시점의 자리에서 시작한다(지금의 해바라기 초기 자리 대신). 같은 사람은 비슷한 자리에 머물고, 변한 곳만 움직인다. 처음 시점만 해바라기에서 시작하므로 여전히 난수가 없다.
- 돌아보기에 `묶음의 변화` 목록 — 시점마다 위 표의 말. 누르면 그 시점 · 그 그룹의 사람들(근거).
- **기록 편향 고지가 더 중요해진다** — 앱을 쓰기 전 시기는 적은 것만 보인다: `앱을 쓰기 시작한 뒤의 시기가 더 정확합니다`. 실사용 시작(2026-10-18) 이전 조각은 옅게.

**비용** — 분기 걸음으로 5년이면 20조각. 조각마다 Louvain 은 밀리초라 백그라운드에서 한꺼번에 미리 셈해 둔다. 배치(조각마다 160번 돌기)가 더 무겁다 — 5,000명이면 조각 하나에 1초 안팎이므로, 사람 수가 많을 때는 시점 막대를 놓았을 때만 그 조각의 배치를 셈한다.

**검증** — 정답표에 시간 사례를 더한다: 두 그룹이 한 시점에 합쳐지는 자료, 한 그룹이 나뉘는 자료, 사람이 중간에 처음 나타나는 자료. 각 시점의 그룹과 변화 판정(새로 생김 · 합쳐짐 · 나뉨 …)을 대조한다.

## 6. 검증 — 여기서 어떻게 확인하나

- Core 순수 함수 `CommunityDetection.louvain(nodes, links, resolution)` + 파이썬 정답표. 작은 그래프: 두 덩어리(→ 2그룹), 별(→ 1그룹), 사슬, 고립점, 끊긴 그룹이 생기는 사례(→ 연결 쪼개기 확인).
- 모듈성 Q 를 파이썬과 소수 6자리로 대조(정해진 차례 · 같은 식이라 맞아야 한다).
- 큰 견본(5,000명) 시간 로그.

## 7. 정할 것

1. 입력 장치: **A 아는 사이 잇기** 를 먼저 할까 (스키마 4판)?
2. 탐지에서 같은 소속을 뺄까 (추천: 뺀다, 이름 짓기에만)?
3. 해상도(크게 묶기 / 잘게 나누기)를 사용자에게 보일까?
4. 그룹 이름을 사용자가 고칠 수 있게(저장)까지 할까, 제안만 할까?
5. **시점에 따른 변화**를 같은 묶음에 넣을까, 그룹 찾기를 먼저 내고 다음 묶음에 넣을까? 창 길이(12개월) · 걸음(분기) 기본값은 이대로 좋은가?
