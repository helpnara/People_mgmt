### 0.2 문서 구성 원칙

- 우선순위는 P0(POC 필수), P1(후속 개선), P2(장기 검토)로 구분한다.
- "해야 한다"는 필수, "할 수 있다"는 선택, "권장한다"는 구현 시 기본 선택을 뜻한다.
- 결정 사항은 부록 A에 모았으며 v0.3에서 모두 확정되었다. 본문은 확정안을 반영한 상태다.

### 0.3 용어집

| 용어 | 영문/코드 | 정의 |
|---|---|---|
| 사람 | Person | 앱의 중심 객체. 사용자가 인연을 맺은 한 명의 인물. |
| 기록 | Record (`RelationshipRecord`) | 특정 사람과 함께한 사건·만남·대화 한 건. 참여자가 1명 이상이고(N:M · ADR-0003), 한 번만 저장되어 참여자 모두의 타임라인에 보인다. |
| 타임라인 | Timeline | 한 사람의 기록을 시간순으로 나열한 화면 영역. |
| 첫 인연 | First encounter | 그 사람을 처음 알게 된 시점과 맥락. 사람의 속성이며 기록이 아니다. |
| 관계 유형 | relationshipType | 나와 그 사람의 관계(동료, 고객 등). |
| 알게 된 경로 | metThrough | 그 사람을 알게 된 계기(직장, 소개 등). |
| 기록 유형 | recordType | 기록의 성격(대화, 식사, 회의 등). |
| 태그 | tag | 사람 또는 기록에 붙이는 짧은 자유 키워드. |
| 표시명 | displayTitle | 제목이 없는 기록을 목록에 보여 줄 때 자동 생성하는 이름. |
| 참여자 | participants | 한 기록에 함께한 사람들. 1명 이상. |
| 소개자 | introducedBy | 그 사람을 나에게 소개한 사람. |
| 관계 지표 | relationship metrics | 기록에서 계산하는 파생 값. 이인 지표(나와 그 사람), 전체 지표(내 네트워크), 구조 지표(사람 간 연결)로 나뉜다. |

### 0.4 확정된 주요 결정 (요약)

- 기술 스택: SwiftUI + SwiftData, iOS 17 이상 (D-1)
- 태그 입력·표시·검색은 P0, 태그 관리는 P1 (D-2)
- 첫 인연은 Person의 속성으로 단일화, 기록 유형에서 "첫 만남" 제거 (D-3)
- 기록은 제목 또는 메모 중 하나만 있으면 저장 가능 (D-4)
- 연락 수단은 휴대전화 · 사무실 · 팩스 · 이메일 · 기타 다섯 칸 (D-5 → D-26)
- 배포는 Apple Developer Program + TestFlight (D-6)
- 앱 잠금은 P1, 기본 꺼짐 (D-7)
- UI 언어는 한국어 전용 (D-8). String Catalog 는 아직 비어 있고 문구는 코드에 있다 — 영어(FR-038)를 넣을 때 옮긴다
- 기록 날짜는 필수이며 기본값은 오늘, 미래 날짜 허용. 사람의 처음 만난 날짜는 선택 (D-9, D-11)
- 번들 식별자 `com.helpnara.slow.connection`, 시리즈 공통 접두어 `com.helpnara.slow` (D-10)
- Xcode 프로젝트는 XcodeGen `project.yml`로 생성 (D-12)
- 타겟·제품 이름 `SlowConnection`, 홈 화면 표시 이름 "느린 인연" (D-13)
- 관계 지표는 사람을 평가하지 않고 관계 상태와 내 네트워크의 모양만 보여 준다. 종합 점수·순위표는 기본 화면에서 제외 (D-14)
- 기록은 여러 사람이 참여할 수 있다(N:M). 소개 관계 필드를 둔다. 둘 다 P0 스키마 (D-15, D-16)
- 이인·전체 지표 P1, 구조 지표 P2 (D-17)
- 1.0은 App Store 무료 공개를 목표로 한다. 스토어 준비는 테스트 기간에 미리 (D-18)
- 유니버설(iPhone·iPad) 빌드, 아이폰 레이아웃 우선 (D-19)
- 작업 브랜치 `claude/slow-connection`, 스토어 판은 `main` (D-20)
- 테스트는 XCTest + 파이썬 정답표(golden JSON) (D-21)
- 컴파일·실행·스크린샷·배포는 GitHub Actions의 macOS 러너가 하고, 순수 로직은 `Packages/Core`로 분리해 리눅스 러너에서 테스트한다 (D-22)

## 1. 제품 개요

### 1.1 배경

일반 연락처 앱은 이름, 전화번호, 이메일, 소속 등 연락처 정보를 관리하는 데 초점이 있다. 그러나 업무와 일상에서 중요한 것은 연락처 자체뿐 아니라 **누구와 어떤 계기로 인연을 맺었고, 함께 무엇을 했으며, 그 관계를 통해 어떤 경험을 쌓았는가**이다.

느린 인연은 사람과의 관계 및 그 사람과 함께한 경험을 지속적으로 기록하고 다시 찾아볼 수 있도록 돕는 개인용 iPhone 앱이다.

### 1.2 제품 비전

> 사람을 저장하는 데서 끝나지 않고, 사람과 나 사이에 쌓인 인연의 역사를 기록한다.

초기에는 개인이 직접 입력하고 관리하는 독립 앱으로 시작한다. 이후 업무 과제, 경력, 문서 등 다른 느린 시리즈 앱과의 연결 가능성을 고려하되, POC 단계에서는 핵심 기록 경험에 집중한다.

### 1.3 핵심 가치

1. **맥락 기록:** 그 사람을 어떻게 알게 되었는지 기록한다.
2. **관계의 축적:** 만남, 대화, 협업 경험을 시간순으로 쌓는다.
3. **재발견:** 검색과 태그를 통해 과거 인연과 기록을 다시 찾는다.
4. **간편한 입력:** 복잡한 CRM이 아니라 짧은 시간 안에 기록할 수 있다.
5. **개인정보 보호:** 개인이 기록을 통제하고 필요 이상의 정보 수집을 피한다.

### 1.4 성공 기준 (POC)

기능 개수가 아니라 다음 질문에 앱이 답할 수 있는지로 판단한다.

> **"이 사람을 어떻게 알게 되었고, 우리는 어떤 시간을 함께했는가?"**

구체적으로는, 사용자가 실기기에서 2주 이상 실제 인연을 기록하며 사용했을 때 (1) 사람 1명 등록과 기록 1건 추가가 각각 30초 안에 끝나고, (2) 3개월 전 기록을 이름 또는 키워드로 10초 안에 다시 찾을 수 있어야 한다.

## 2. 목표와 범위

### 2.1 POC 목표

사용자가 다음 핵심 흐름을 수행할 수 있는 앱을 만든다.

1. 사람을 새로 등록한다.
2. 그 사람을 알게 된 계기와 첫 인연 메모를 기록한다.
3. 사람별 상세 화면에서 기본 정보와 관계 기록을 확인한다.
4. 새로운 만남이나 함께한 일을 타임라인에 추가한다.
5. 이름, 키워드 또는 태그로 사람을 검색한다.

### 2.2 초기 버전(P0) 범위

**포함**
- 사람 목록 조회(이름순 정렬)
- 사람 추가·수정·삭제
- 사람별 기본 정보(이름, 소속, 직무)
- 관계 유형 및 알게 된 경로 기록(선택지 + 직접 입력)
- 첫 인연(처음 만난 날짜, 첫 인연 메모)
- 사람별 기록 추가·수정·삭제, 기록 상세 보기
- 기록에 함께한 사람(참여자) 여러 명 지정
- 소개 관계(누구의 소개로 알게 되었는지) 기록
- 시간순 타임라인
- 사람·기록 태그 입력, 표시, 태그 검색
- 키워드 검색(사람·기록 텍스트)
- 기기 내 데이터 저장과 앱 재실행 후 유지
- 입력 검증, 동명이인 참고 안내, 미저장 변경 보호
- 빈 상태, 오류, 삭제 확인 안내

**초기 버전에서 제외**
- 자동 주소록 전체 동기화
- SNS 계정 연동 및 자동 정보 수집
- 명함 OCR 및 자동 연락처 생성
- AI를 이용한 대화 분석 또는 인물 평가
- 팀 공유, 공동 편집, 기업용 관리자 기능
- 자동 메시지 발송 및 후속 연락 추천
- 복잡한 CRM 영업 파이프라인
- 다른 느린 앱과의 실시간 양방향 연동
- 클라우드 동기화(iCloud/CloudKit)

제외 기능은 사용성 검증 이후 별도 검토한다.

## 3. 주요 사용자와 사용 시나리오

### 3.1 주요 사용자

- 업무상 만나는 동료, 상사, 후배, 고객, 협력사와의 관계를 기억하고 싶은 개인
- 프로젝트를 함께한 사람과 협업 이력을 정리하려는 사용자
- 시간이 지난 뒤에도 만남의 맥락과 대화 내용을 다시 확인하고 싶은 사용자
- 개인 네트워크를 장기적으로 관리하고 싶은 사용자

POC 단계의 실제 사용자는 개발자 본인 1명이다. 따라서 온보딩·튜토리얼은 빈 상태 안내 수준으로 최소화한다.

### 3.2 대표 시나리오

**시나리오 A: 처음 만난 사람 등록**
1. 사용자가 사람 목록에서 `사람 추가`를 선택한다.
2. 이름을 입력한다.
3. 관계 유형과 알게 된 경로를 선택지에서 고르거나 직접 입력한다.
4. 처음 만난 날짜와 첫 인연 메모를 입력한다. 둘 다 비워도 된다.
5. 태그를 입력한다(선택).
6. 저장하면 사람 상세 화면으로 이동하고, 타임라인에는 첫 인연 항목이 시작점으로 표시된다.

**시나리오 B: 기존 인연의 새로운 기록 추가**
1. 사용자가 사람 목록에서 특정 인물을 선택한다.
2. 사람 상세에서 `기록 추가`를 선택한다.
3. 날짜(기본값 오늘)를 확인하고 기록 유형을 고른다.
4. 제목 또는 메모를 입력한다. 장소, 태그, 함께한 사람은 선택이다.
5. 저장하면 해당 사람의 타임라인에 기록이 날짜 위치에 맞게 추가된다. 함께한 사람을 지정했다면 그 사람들의 타임라인에도 같은 기록이 나타난다.

**시나리오 C: 과거 기록 찾기**
1. 사용자가 사람 목록 상단의 검색창에 이름, 키워드 또는 태그를 입력한다.
2. 입력과 동시에 일치하는 사람이 표시되고, 각 결과에 어떤 항목이 일치했는지 근거가 함께 보인다.
3. 결과에서 사람을 선택하면 상세 화면에서 기본 정보와 과거 기록을 확인한다.

**시나리오 D: 기록 수정과 삭제**
1. 사용자가 타임라인에서 기록을 선택해 기록 상세를 본다.
2. `편집`으로 날짜·유형·제목·메모를 수정하고 저장한다.
3. 잘못 입력한 기록은 `삭제`를 선택하고, 확인 대화상자에서 삭제를 확정한다.
4. 사람 자체를 삭제할 때는 "기록 N건이 함께 삭제됩니다"라는 안내를 보고 확정한다.

**시나리오 E: 처음 만난 날짜를 모를 때**
1. 사용자가 오래전 인연을 등록하면서 처음 만난 날짜를 비워 둔다.
2. 첫 인연 메모에 "2015년 무렵 OO 프로젝트에서"라고 적는다.
3. 상세 화면에서는 날짜 대신 "날짜 미상"으로 표시되고, 나중에 수정 화면에서 날짜를 채울 수 있다.

**시나리오 G: 여러 사람과 함께한 기록**
1. 사용자가 팀 회식을 기록하려고 팀장 A의 상세에서 `기록 추가`를 연다.
2. `함께한 사람`에서 B, C를 추가한다.
3. 저장하면 A, B, C 세 사람의 타임라인에 같은 기록이 "외 2명" 표시와 함께 나타난다.
4. 나중에 B를 삭제하면 이 기록은 남고 B만 참여자에서 빠진다.

**시나리오 F: 동명이인 등록**
1. 사용자가 이미 등록된 이름과 같은 이름을 입력한다.
2. 입력 필드 아래에 "같은 이름이 1명 있습니다: 홍길동 (OO회사)"라는 참고 안내가 보인다.
3. 사용자는 기존 사람을 열어 볼 수도 있고, 그대로 새로 등록할 수도 있다. 등록은 막지 않는다.

### 4.1 내비게이션 구조

```text

└ 사람 목록 (홈)
   ├ 검색 모드 (같은 화면, 검색창 활성화 시 결과 표시)
   ├ [+] 사람 추가 ........................ 모달 시트
   ├ [⚙] 설정 (P1) ........................ 모달 시트

      ├ [편집] 사람 수정 .................. 모달 시트
      ├ [기록 추가] 기록 추가 ............. 모달 시트
      ├ [삭제] 확인 → 삭제 후 목록으로 복귀
      └ 기록 상세 ......................... 푸시
         ├ [편집] 기록 수정 ............... 모달 시트
         └ [삭제] 확인 → 삭제 후 사람 상세로 복귀
```

**아이패드 (넓은 폭 · D-49 · 이슈 32).** 같은 화면들을 칸으로 나눠 나란히 둔다 — 아이폰은 위 구조 그대로.

```text
NavigationSplitView
├ 왼쪽 바: 사람 · 내 인맥(관계도 · 특성 · 돌아보기 · 입력 상태) · 설정
└ 오른쪽
   ├ 사람: 사람 목록 (왼쪽) │ 사람 상세 (오른쪽 · 안에서 기록 상세로 푸시)
   ├ 관계도: 위 4분의 3 관계도(거르기 한 줄 · 시점 설명 한 줄) ─ 아래 4분의 1 누른 사람의 상세 (늘 둔다 · 왼쪽 바는 그대로)
   ├ 특성 · 돌아보기 · 입력 상태: 그 화면 (안에서 목록 · 사람으로 푸시)
   └ 설정
```

- 추가·수정은 모달 시트로 열고, 조회는 푸시로 연다. 이렇게 하면 "지금 입력 중인가, 보고 있는가"가 화면 형태로 구분된다.
- 모든 입력 화면은 상단에 `취소`와 `저장` 버튼을 둔다. 저장 조건을 만족하지 않으면 `저장`을 비활성화한다.

### 4.2 화면별 정의

#### 4.2.1 사람 목록 (홈)

| 항목 | 내용 |
|---|---|
| 구성 | 검색창(상단 고정), 사람 행 목록, `사람 추가` 버튼(툴바), 설정 버튼(P1) |
| 사람 행 | 1줄: 이름. 2줄: 소속 · 직무 (둘 다 없으면 관계 유형, 그것도 없으면 생략). 우측 보조: 마지막 기록일(P1). 사진 썸네일(P1) |
| 정렬 | 이름순(NFC · 소문자 코드 순 — 파이썬 정답표와 같은 차례, `Core.NameSort`) · 최근 기록순 · 최근 등록순 (FR-027). 섹션 인덱스는 사람 50명 이상일 때 표시 권장 |
| 동작 | 행 탭 → 사람 상세. 행 스와이프 → 삭제(확인 필요). 검색창 입력 → 검색 모드 |
| 빈 상태 | 등록된 사람이 없으면 앱 목적 한 줄 + `첫 사람 등록하기` 버튼을 표시한다. |
| 검색 빈 결과 | "'검색어'와 일치하는 사람이 없습니다" 안내 |
| 홈 최근 기록(P1) | 목록 상단에 최근 기록 3건 카드 |

#### 4.2.2 사람 추가·수정

| 항목 | 내용 |
|---|---|
| 필드 순서 | 이름(필수) → 사진(P1) → 소속 → 직무 → 관계 유형 → 알게 된 경로 → 소개한 사람(경로가 "소개"일 때만 표시) → 처음 만난 날짜 → 첫 인연 메모 → 태그 → 별명·호칭(P1) → 연락 수단 메모(P1) |
| 이름 | 텍스트, 자동 포커스. 입력 중 동명이인이 있으면 필드 아래 참고 안내 |
| 관계 유형 / 알게 된 경로 | 선택지 칩(6.3절) + `직접 입력`. 하나만 선택 가능. 선택 해제 가능 |
| 소개한 사람 | 알게 된 경로가 "소개"일 때 나타나는 사람 선택기. 등록된 사람 목록에서 1명 선택, 검색 가능. 자기 자신은 선택 불가. 비워 둘 수 있다 |
| 처음 만난 날짜 | 날짜 선택기(일 단위). 기본값 없음(비어 있음). `지우기` 제공 |
| 첫 인연 메모 | 여러 줄 텍스트. 안내 문구 "어떤 계기로 알게 되었나요?" |
| 태그 | 쉼표 또는 줄바꿈으로 구분해 입력. 입력된 태그는 칩으로 표시, 칩 탭으로 제거 |
| 저장 조건 | 이름이 공백 제외 1자 이상 |
| 취소 | 변경 사항이 있으면 "변경 사항을 버리시겠습니까?" 확인 |
| 저장 후 | 추가: 사람 상세로 이동. 수정: 상세로 복귀하고 변경 반영 |

#### 4.2.3 사람 상세

| 항목 | 내용 |
|---|---|
| 상단 | 이름, 소속 · 직무, 관계 유형 칩, 알게 된 경로, 소개자가 있으면 "OOO의 소개로"(탭하면 소개자 상세로 이동), 태그 칩, 사진(P1) |
| 소개한 인연 | 이 사람이 소개한 사람이 있으면 "소개한 인연 N명" 행. 탭하면 목록 |
| 관계 돌아보기(P1) | 이인 지표 카드(5.5절). 기록이 임계값 미만이면 안내 문구로 대체 |
| 첫 인연 영역 | 처음 만난 날짜(없으면 "날짜 미상")와 첫 인연 메모. 둘 다 없으면 "첫 인연을 기록해 보세요" 안내와 편집 바로가기 |
| 타임라인 | 이 사람이 참여자인 모든 기록. 최신순. 각 행: 유형 아이콘, 날짜, 표시명, 메모 첫 줄(1줄 말줄임), 장소(있을 때), 다른 참여자가 있으면 "외 N명", 태그 |
| 시작점 | 타임라인 맨 아래에 첫 인연 항목을 고정 표시한다. 저장된 기록이 아니므로 스와이프 삭제 대상이 아니며, 탭하면 사람 수정 화면으로 간다 |
| 도구 | `기록 추가`(눈에 띄는 위치, 한 손 조작 가능한 하단 우측 권장), 메뉴(편집, 삭제, 내보내기 P1) |
| 빈 타임라인 | 기록이 없으면 "아직 기록이 없습니다. 함께한 일을 남겨 보세요" + `기록 추가` |
| 동작 | 기록 행 탭 → 기록 상세. 기록 행 스와이프 → 삭제(확인 필요) |

#### 4.2.4 기록 추가·수정

| 항목 | 내용 |
|---|---|
| 필드 순서 | 날짜(기본값 오늘) → 기록 유형(기본값 "대화") → 제목 → 메모 → 장소 → 함께한 사람 → 태그 → 도움 방향(P1, 유형이 "도움"일 때만) |
| 날짜 | 날짜 선택기(일 단위). 미래 날짜도 허용한다(예정된 만남을 미리 적는 경우). 대략 날짜(P1, FR-033) |
| 기록 유형 | 선택지 칩(6.4절). 반드시 하나 선택 |
| 제목 | 한 줄. 비울 수 있다 |
| 함께한 사람 | 기록을 연 사람이 기본 참여자로 고정되어 있다. `추가`로 등록된 사람을 검색해 여러 명 추가할 수 있고, 추가한 사람은 칩으로 표시되며 탭해 제거한다. 참여자는 항상 1명 이상이다 |
| 메모 | 여러 줄. 긴 글 입력에 적합한 높이, 키보드 위로 스크롤 |
| 저장 조건 | 제목 또는 메모 중 하나가 공백 제외 1자 이상 |
| 취소 | 변경 사항 있으면 버리기 확인 |
| 저장 후 | 추가: 사람 상세로 복귀하고 새 기록이 날짜 위치에 보임. 수정: 기록 상세로 복귀 |

#### 4.2.5 기록 상세

| 항목 | 내용 |
|---|---|
| 구성 | 유형 아이콘·이름, 날짜, 표시명, 장소, 참여자 목록(각각 탭하면 그 사람 상세로 이동), 메모 전문(스크롤), 태그, 생성·수정 시각(작게) |
| 도구 | `편집`, `삭제` |
| 메모 | 선택·복사 가능. 긴 메모도 끊김 없이 읽을 수 있어야 한다 |

#### 4.2.6 검색 결과 (사람 목록의 검색 모드)

| 항목 | 내용 |
|---|---|
| 결과 단위 | 사람 |
| 결과 행 | 이름 + 일치 근거 1줄. 예: "기록 '분기 회의' 메모에서 일치", "태그 #멘토 일치", "소속 일치" |
| 정렬 | 이름 일치 → 태그 일치 → 그 밖의 사람 필드 일치 → 기록 필드 일치 순. 같은 그룹 안에서는 이름순 |
| 동작 | 행 탭 → 사람 상세. 기록에서 일치한 경우 해당 기록으로 스크롤·강조는 P1(FR-034) |
| 공동 기록 | 기록 필드에서 일치하면 그 기록의 참여자 전원이 각각 결과에 나타난다 |

#### 4.2.7 설정 (P1)

앱 버전, 개인정보 안내, 앱 잠금 토글(FR-029), 백업 내보내기·가져오기(FR-018), 전체 데이터 삭제(2단계 확인).

### 4.3 기본 탐색 원칙

- 앱의 중심 객체는 전화번호가 아니라 **사람(Person)** 이다.
- 사람 상세 화면은 그 사람과의 인연을 이해하는 중심 화면이다.
- 만남과 협업 기록은 흩어지지 않고 참여한 모든 사람의 타임라인에 연결된다. 기록 한 건은 한 번만 저장되고 여러 타임라인에서 보인다.
- 주요 기능은 iPhone에서 한 손으로 사용하기 쉬운 단순한 탐색 구조를 지향한다. 자주 쓰는 `기록 추가`는 화면 하단에서 닿을 수 있어야 한다.
- 기본 흐름의 깊이는 3단계(목록 → 사람 상세 → 기록 상세)다. 내 인맥에서 들어가면 내 인맥 → 목록 → 사람 → 기록까지 깊어질 수 있고, 모든 화면은 값 하나로 열어 뒤로 가기가 늘 맞는다 (이슈 16).

### 5.3 검색 명세 (FR-010, FR-011)

**검색 대상 필드**

| 엔터티 | 필드 | 비고 |
|---|---|---|
| Person | name, organization, role, relationshipType, metThrough, firstNote, tags | nickname, contactNote는 P1 |
| Record | title, note, location, tags | |

**일치 규칙**
- 부분 문자열 일치. 대소문자와 발음 구별 기호를 무시한다(`localizedStandardContains` 수준).
- 한글은 저장·비교 시 NFC로 정규화한다. 초성 검색은 P2(FR-036).
- 검색어를 공백으로 나눈 각 단어가 모두(AND) 그 사람의 대상 필드 어딘가에 포함되어야 한다. 단어마다 다른 필드에 있어도 된다.
- 태그 검색은 `#멘토`처럼 `#`을 붙이면 태그 필드만 대상으로 하고, 붙이지 않으면 태그를 포함한 전체 필드를 대상으로 한다.
- 1자부터 검색한다. 입력 후 300ms 디바운스로 결과를 갱신한다.

**결과 표시**
- 결과 단위는 사람이며 중복 없이 1회 표시한다.
- 각 결과에 일치 근거를 1줄 표시한다. 우선순위: 이름 > 태그 > 그 밖의 사람 필드 > 기록 필드. 기록 필드 일치는 "기록 '표시명'의 메모" 형식으로 표시한다.
- 정렬은 4.2.6절을 따른다.

### 5.5 관계 지표 명세 (FR-044~049)

**표현 원칙** (13절 원칙의 구체화)
1. 단일 종합 점수와 사람 순위표를 기본 화면에 두지 않는다.
2. 모든 지표는 탭하면 근거가 된 기록을 보여 준다.
3. 지표 화면에는 "내가 기록한 범위 기준"임을 고지한다. 적지 않은 만남은 계산되지 않는다.
4. 기록 수가 임계값 미만이면 지표 대신 "기록이 더 쌓이면 표시됩니다"를 보여 준다.
5. 중립적 언어를 쓴다. "약한 관계"가 아니라 "최근 기록 없음".

**이인 지표 (P1)**

| 지표 | 정의 | 최소 기록 수 |
|---|---|---|
| 기록 수 | 전체 건수와 최근 12개월 건수 | 1 |

| 지표 | 정의 |
|---|---|
| 활성 인원 | 최근 12개월 안에 기록이 있는 사람 수 |
| 신규 인연 | 처음 만난 날이 올해인 사람 수 |

**구조 지표 (P2)**
- 연결: 같은 기록에 참여한 두 사람 사이에 연결을 만들고 가중치는 공동 기록 수로 한다. 소개 관계도 가중치 1의 연결로 포함한다. 소속·태그 공유는 기본적으로 연결로 쓰지 않는다.
- 커뮤니티: Louvain 또는 Label Propagation. 시드를 고정해 결과가 재현되게 한다. 그룹 이름은 구성원 다수의 소속·태그로 제안한다.
- 매개 역할: ego를 제외한 그래프에서 Brandes 매개 중심성. 상위 소수를 "그룹을 잇는 사람"으로 표시하되 수치는 숨긴다.
- 제외: 근접 중심성, 고유벡터·PageRank, 중개 역할 유형 분류. 자아 중심 네트워크에서 의미가 없거나 설명이 어렵다.

**계산과 캐시**
- 이인·전체 지표는 상세 화면 진입 시 즉시 계산한다(기록 1회 순회).
- 구조 지표는 앱 실행 후와 데이터 변경 후 백그라운드에서 재계산하고 `MetricsSnapshot`으로 캐시한다. 메인 스레드를 막지 않는다.
- 모든 지표 계산은 UI와 분리된 순수 함수로 두고 소형 그래프(삼각형, 별, 두 덩어리)로 단위 테스트한다.
- 서드파티 라이브러리 없이 Swift로 직접 구현한다.

- `displayTitle`: title이 있으면 title. 없으면 note의 첫 줄을 40자까지. 그것도 없을 수 없으므로 항상 값이 있다.

### 6.5 데이터 관계와 확장 지점

```text
Person N ───── M Record      (participants)
Person 0..1 ── N Person      (introducedBy)
```

- 한 사람은 여러 기록에 참여할 수 있고, 한 기록에는 1명 이상이 참여한다. 대부분의 기록은 참여자가 1명이며, 이 경우 사용자 경험은 1:N과 같다.
- **사람 삭제 규칙:** 그 사람이 유일한 참여자인 기록은 삭제한다. 다른 참여자가 있는 기록에서는 참여자 목록에서만 제거한다. 그 사람을 `introducedBy`로 가진 사람들의 필드는 nil로 바꾼다.
- **기록 삭제 규칙:** 기록만 삭제되고 참여자는 남는다.
- **사람 간 연결:** 공동 참여 기록과 소개 관계에서 계산하고, 기록 없이 서로 아는 사이는 `Tie` 로 저장한다 (스키마 4판 · D-30).
- **느린 시리즈 연동 예약**: 추후 `ExternalReference { sourceApp: String, entityKind: String, externalId: String, label: String }` 엔터티를 두고 Person·Record가 0..N개를 가지도록 확장한다. POC 스키마에는 넣지 않는다. 모든 ID가 UUID이므로 다른 앱에서 이 앱의 사람·기록을 참조할 수 있다.
- **태그**: POC에서는 문자열 배열로 저장한다. 태그 관리(FR-026)가 필요해지면 `Tag` 엔터티로 옮기되, 문자열 배열에서 자동 생성할 수 있으므로 마이그레이션은 단방향이다.

### 6.6 스키마 버전과 마이그레이션

- 첫 릴리스부터 스키마에 버전(`SchemaV1`)을 부여하고, 이후 변경은 새 버전 + 마이그레이션 단계로 추가한다.
- P1 필드(nickname, contactNote, precision 등)는 추가 시 모두 선택 또는 기본값이 있어 경량 마이그레이션으로 처리한다.
- 백업 JSON(FR-018)에는 `schemaVersion`을 포함해 가져오기 시 변환 가능하게 한다.

## 7. 입력 및 사용성 규칙

### 7.1 원칙

1. **최소 입력:** 사람은 이름만, 기록은 제목 또는 메모 중 하나만 있으면 저장된다.
2. **단계적 기록:** 사람을 먼저 저장한 뒤 추가 정보를 보완할 수 있다.
3. **빠른 기록:** 사람 상세 화면에서 새 기록을 바로 추가할 수 있고, 날짜·유형은 기본값이 채워져 있다.
4. **명확한 날짜:** 처음 만난 날짜는 모르면 비워 둔다. 기록 날짜는 기본값 오늘이며 바꾸기 쉽다.
5. **중복 안내:** 동일 이름이 이미 있을 때 참고 안내를 제공하되 동명이인 등록을 막지 않는다.
6. **빈 상태 안내:** 등록된 사람이 없을 때 앱의 목적과 첫 등록 방법을 안내한다.
7. **삭제 안전성:** 삭제 전에 대상과 삭제 범위를 명확하게 보여 준다.
8. **입력 보호:** 입력 중인 내용은 실수로 잃지 않는다(미저장 변경 확인, 저장 실패 시 내용 유지).

### 7.2 입력 검증 규칙

| 필드 | 규칙 | 위반 시 |
|---|---|---|
| 이름 | 앞뒤 공백 제거 후 1~100자. 공백만 입력 불가 | 저장 비활성화, 필드 아래 "이름을 입력하세요" |
| 소속, 직무, 장소, 관계 유형(직접 입력), 알게 된 경로(직접 입력) | 각 100자 이하(관계 유형은 50자) | 초과 입력 차단, 남은 글자 수 표시 |
| 기록 제목 | 100자 이하 | 초과 입력 차단 |
| 첫 인연 메모 | 5,000자 이하 | 초과 입력 차단 |
| 기록 메모 | 20,000자 이하 | 초과 입력 차단 |
| 기록 제목/메모 | 둘 다 공백만이면 저장 불가 | 저장 비활성화, "제목이나 메모를 입력하세요" |

모든 텍스트는 저장 전에 유니코드 NFC로 정규화한다.

### 7.3 날짜 정책

- `firstMetDate`와 `occurredAt`은 날짜만 의미가 있다. 시간대 변경으로 하루가 밀리지 않도록 사용자 캘린더 기준 정오로 정규화해 저장한다.
- 표시 형식은 기기 로케일과 설정을 따른다(예: 2026년 10월 17일). 목록에서는 연도가 올해면 생략할 수 있다.
- 타임라인은 연도 또는 월 단위 섹션 헤더로 묶어 표시하는 것을 권장한다.

### 7.4 미저장 변경 보호 (FR-022)

- 입력 화면에서 원래 값과 다른 필드가 하나라도 있으면 "변경 사항 있음" 상태다.
- 이 상태에서 `취소`를 누르거나 시트를 아래로 내리면 "변경 사항을 버리시겠습니까?" 대화상자를 띄운다. 선택지: `계속 편집`, `버리기`.
- 변경 사항이 없으면 바로 닫는다.

### 7.5 저장 실패 처리 (FR-023)

- 저장 실패 시 입력 화면을 닫지 않고 내용을 유지한다.
- 안내 문구: "저장하지 못했습니다. 기기 저장 공간이 부족하지 않은지 확인한 뒤 다시 시도해 주세요." + `다시 시도` 버튼.
- 반복 실패 시 사용자가 내용을 복사해 둘 수 있도록 메모 필드를 선택 가능 상태로 유지한다.
- 실패 원인은 로컬 로그(os_log)에만 남기고 외부로 전송하지 않는다.

### 8.2 저장 및 안정성

- POC에서는 기기 내 저장을 기본으로 한다. 네트워크 없이 모든 기능이 동작한다.
- 앱을 종료(강제 종료, 기기 재부팅 포함)하고 다시 실행해도 데이터가 유지되어야 한다.
- 저장은 사용자가 `저장`을 누른 시점에 즉시 디스크에 반영한다. 지연 저장으로 인한 유실이 없어야 한다.
- 저장 실패 시 7.5절을 따른다.
- 저장소 구현은 향후 백업·복원 또는 동기화로 확장할 수 있도록 데이터 계층을 분리한다(8.1 아키텍처).
- 크래시 리포팅·원격 로깅은 포함하지 않는다. 개발 중에는 Xcode Organizer의 기기 로그로 충분하다.

### 8.3 개인정보 보호

- 연락처 및 관계 기록은 민감한 개인 정보로 취급한다.
- 사용자의 명시적 동의와 행동 없이 주소록, 사진, 외부 서비스에서 정보를 자동 수집하지 않는다. 사진 선택(P1)은 PhotosPicker를 사용해 선택한 사진 1장에만 접근하고, 사진 보관함 전체 권한을 요청하지 않는다.
- 분석·추적 SDK, 광고 식별자, 원격 로깅을 포함하지 않는다. 네트워크 통신을 전혀 하지 않는다.
- **데이터 위치 고지:** 앱 데이터는 기기 안에만 저장된다. 다만 사용자가 iCloud 백업 또는 컴퓨터 백업을 켜 두었다면 iOS가 다른 앱 데이터와 함께 이 앱의 데이터도 백업에 포함한다. 이는 앱이 클라우드 동기화를 하는 것과 다르며, 설정 화면의 개인정보 안내(P1)에 이 사실을 적는다.
- 내보내기·백업(P1) 파일에는 개인정보가 포함됨을 실행 전에 안내한다.
- 클라우드 동기화를 도입할 때는 저장 위치, 접근 권한, 삭제 정책을 별도 정의한다.
- App Store에 배포할 경우 개인정보 처리방침 URL과 App Privacy 라벨("데이터 수집 안 함")이 필요하다.

### 8.4 보안

- 저장 파일에는 iOS 데이터 보호 "처음 잠금 해제 후 보호(NSFileProtectionCompleteUntilFirstUserAuthentication)"를 적용한다 (D-48). 기기를 켠 뒤 한 번 잠금을 풀기 전에는 읽을 수 없다. iCloud 동기화(D-42)부터 앱은 잠긴 동안에도 다른 기기의 변경을 받으러 깨어나므로 "완전 보호"는 쓰지 않는다 — 빌드 21 에서 잠긴 동안 읽다가 앱이 꺼졌다(이슈 31). 화면 쪽 셈은 앱이 앞에 있고 잠기지 않았을 때만 한다.
- 앱 잠금(FR-029, P1)은 LocalAuthentication을 사용하며, 생체 인증 실패 시 기기 암호로 대체한다. 잠금 상태에서는 앱 전환기 스냅샷에 내용이 보이지 않도록 가림 화면을 표시한다.
- 외부 입력(백업 가져오기, P1)은 스키마 검증 후에만 반영한다.

### 8.5 성능

기준 데이터 규모: 사람 5,000명, 기록 50,000건, 메모 평균 500자, 최대 20,000자. (2026-10-18 하루 10명 입력 전제로 1,000명·10,000건에서 올림. CI가 이 규모의 견본으로 화면 시간을 로그에 남긴다.)

| 항목 | 목표 |
|---|---|
| 콜드 실행 후 사람 목록 표시 | 1.0초 이내 |
| 사람 상세(기록 500건) 표시 | 0.5초 이내 |
| 검색 결과 갱신(디바운스 제외) | 0.5초 이내 |
| 저장 완료 | 0.3초 이내 |
| 스크롤 | 목록·타임라인·긴 메모에서 끊김 없음(60fps 기준) |
| 앱 용량 | 사진 제외 데이터 50MB 이하 |

검색은 메인 스레드를 막지 않아야 한다.

### 8.6 접근성

| 항목 | 요구 |
|---|---|
| Dynamic Type | 모든 텍스트가 시스템 글자 크기를 따른다. 접근성 크기(AX1~AX5)에서도 핵심 기능(등록, 기록 추가, 검색, 삭제)을 사용할 수 있어야 하며 글자가 잘리지 않는다 |
| VoiceOver | 모든 버튼·입력 필드에 레이블이 있다. 기록 행은 "유형, 날짜, 표시명" 순으로 읽힌다. 아이콘 전용 버튼에는 접근성 레이블을 둔다 |
| 색상 | 정보 구분을 색상에만 의존하지 않는다(유형은 아이콘 + 라벨). 텍스트 대비 4.5:1 이상 |
| 터치 영역 | 모든 탭 가능 요소 44×44pt 이상 |
| 다크 모드 | 라이트·다크 모두 지원하고 시스템 설정을 따른다 |
| 동작 줄이기 | Reduce Motion 설정 시 전환 애니메이션을 줄인다 |
| 긴 메모 | 입력·읽기 모두 스크롤과 선택·복사가 자연스러워야 한다 |

### 8.7 언어와 로케일

- UI 언어는 한국어 전용이다. 모든 사용자 노출 문자열은 String Catalog로 관리해 추후 영어(FR-038)를 추가할 수 있게 한다.
- 날짜·시간·상대 시간("3개월 전") 표기는 기기 로케일 포맷터를 사용한다.
- 이름 정렬은 NFC · 소문자 코드 순으로 한다 — 리눅스 정답표(파이썬)와 기기가 같은 차례를 내도록 정한 것이다 (`Core.NameSort` · 가정 A5).

### 8.8 배포

- 1.0은 App Store 무료 공개를 목표로 한다 (D-18). 그 전까지는 TestFlight 내부 테스트로 본인 기기에 설치한다(빌드당 90일 유효).
- 빌드·서명·업로드는 GitHub Actions의 `testflight.yml`이 App Store Connect API 키(팀 단위, 느린 시리즈 공통)로 수행한다. 절차와 처음 한 번 할 일은 `docs/06-ci.md`.
- 번들 식별자는 `com.helpnara.slow.connection`이다. 느린 시리즈 공통 접두어는 `com.helpnara.slow`이며, 이후 앱은 같은 접두어 아래 영어 이름으로 둔다(예: 느린 나이테 `com.helpnara.slow.rings`). 앱 그룹이 필요해지면 `group.com.helpnara.slow`를 사용한다.

## 9. 수용 기준

POC는 아래 조건을 모두 충족하면 핵심 기능 구현 완료로 판단한다. 각 항목은 실기기에서 수동으로 확인하거나 자동 테스트로 검증한다.

### 9.1 사람 관리

- [ ] **AC-01** 이름만 입력하고 저장하면 사람이 생성되고 상세 화면으로 이동한다.
- [ ] **AC-02** 이름을 비우거나 공백만 입력하면 저장 버튼이 비활성화된다.
- [ ] **AC-03** 관계 유형과 알게 된 경로를 선택지에서 고르거나 직접 입력해 저장하면 상세 화면에 표시된다.
- [ ] **AC-04** 처음 만난 날짜를 비우고 첫 인연 메모만 저장하면 상세에 "날짜 미상"과 메모가 표시된다.
- [ ] **AC-05** 등록한 사람이 목록에 이름순으로 나타난다.
- [ ] **AC-06** 이미 있는 이름을 입력하면 참고 안내가 보이고, 그대로 저장하면 동명이인이 모두 목록에 남는다.
- [ ] **AC-07** 사람 정보의 모든 필드를 수정하고 저장하면 상세와 목록에 즉시 반영된다.
- [ ] **AC-08** 단독 기록 3건이 있는 사람을 삭제하려 하면 "기록 3건을 모두 삭제" 문구가 보이고, 확정하면 사람과 기록이 모두 사라진다.
- [ ] **AC-33** 알게 된 경로를 "소개"로 고르면 소개한 사람 선택이 나타나고, 저장 후 양쪽 상세에서 서로를 확인하고 이동할 수 있다. 소개자를 삭제하면 소개받은 사람의 소개자 표시가 사라진다.

### 9.2 기록과 타임라인

- [ ] **AC-09** 기록 추가 화면을 열면 날짜는 오늘이고, 유형은 처음에는 대화 · 그다음부터는 지난번에 새로 쓴 기록의 유형이 골라져 있다 (D-46).
- [ ] **AC-10** 제목 없이 메모만 입력해 저장하면 타임라인에 메모 첫 줄이 표시명으로 보인다.
- [ ] **AC-11** 제목과 메모가 모두 비어 있으면 저장 버튼이 비활성화된다.
- [ ] **AC-12** 날짜가 다른 기록 3건을 입력 순서와 다르게 추가해도 타임라인은 날짜 최신순으로 표시된다.
- [ ] **AC-13** 같은 날짜의 기록 2건은 나중에 만든 것이 위에 표시된다.
- [ ] **AC-14** 처음 만난 날짜가 있는 사람의 타임라인 맨 아래에 첫 인연 시작점이 표시되고, 탭하면 사람 수정 화면이 열린다.
- [ ] **AC-15** 기록을 탭하면 20,000자 메모 전문을 끊김 없이 스크롤해 읽을 수 있다.
- [ ] **AC-16** 기록을 수정하고 저장하면 상세와 타임라인에 반영되고 수정 시각이 갱신된다.
- [ ] **AC-17** 기록 삭제 전에 확인 대화상자가 표시되고, 취소하면 기록이 남는다.
- [ ] **AC-34** A의 상세에서 B, C를 함께한 사람으로 추가해 기록을 저장하면 세 사람의 타임라인에 같은 기록이 "외 2명"과 함께 나타나고, 기록 상세의 참여자에서 B를 탭하면 B의 상세로 이동한다.
- [ ] **AC-35** 공동 기록 1건과 단독 기록 2건이 있는 B를 삭제하려 하면 "기록 2건 삭제, 함께한 기록 1건에서 제외" 문구가 보이고, 확정 후 공동 기록은 A와 C의 타임라인에 남는다.

### 9.3 태그와 검색

- [ ] **AC-18** 사람과 기록에 태그를 여러 개 입력하면 칩으로 표시되고, `#멘토`, `멘토 `, `멘토`는 하나의 태그로 저장된다.
- [ ] **AC-19** 이름 일부를 입력하면 해당 사람이 결과에 나타난다.
- [ ] **AC-20** 어떤 기록의 메모에만 있는 단어를 검색하면 그 사람이 결과에 나타나고 근거로 해당 기록이 표시된다. 공동 기록이면 참여자 전원이 결과에 나타난다.
- [ ] **AC-21** 태그로 검색하면 그 태그를 가진 사람(기록의 태그 포함)이 결과에 나타난다.
- [ ] **AC-22** 두 단어를 띄어 입력하면 두 단어가 모두 포함된 사람만 나타난다.
- [ ] **AC-23** 대소문자가 다른 영문 검색어도 일치한다.
- [ ] **AC-24** 일치하는 사람이 없으면 빈 결과 안내가 표시된다.

### 9.4 안정성과 안내

- [ ] **AC-25** 데이터를 입력한 뒤 앱을 강제 종료하고 다시 실행해도 모든 데이터가 유지된다.
- [ ] **AC-26** 사람이 없을 때 홈에 앱 목적과 첫 등록 버튼이 표시된다.
- [ ] **AC-27** 기록이 없는 사람의 상세에 기록 추가 안내가 표시된다.
- [ ] **AC-28** 입력 화면에서 내용을 바꾼 뒤 취소하면 버리기 확인이 뜨고, 바꾸지 않았으면 바로 닫힌다.
- [ ] **AC-29** 저장 실패를 모사(테스트용 실패 저장소)했을 때 입력 내용이 유지되고 재시도 안내가 표시된다.

### 9.5 접근성과 표시

- [ ] **AC-30** 가장 큰 접근성 글자 크기에서 사람 등록, 기록 추가, 검색, 삭제를 수행할 수 있다.
- [ ] **AC-31** 다크 모드에서 모든 화면의 텍스트와 아이콘이 읽힌다.
- [ ] **AC-32** VoiceOver로 사람 목록 → 상세 → 기록 추가 → 저장까지 진행할 수 있다.

## 10. POC 개발 순서

각 단계는 "완료 기준"을 충족해야 다음 단계로 넘어간다.

### 1단계: 기본 골격
- Xcode 프로젝트 구성(SwiftUI, iOS 17, String Catalog)
- 데이터 모델(`Person`, `Record`) 및 `SchemaV1` 정의
- 저장소 프로토콜과 SwiftData 구현, 인메모리 테스트 구현
- 기본 내비게이션 뼈대
- **완료 기준:** 저장소 CRUD 단위 테스트 통과, 앱 실행 시 빈 목록 표시

### 2단계: 사람 관리
- 사람 목록(정렬, 빈 상태)
- 사람 추가·수정 화면(검증, 선택지 칩, 미저장 보호, 동명이인 안내)
- 사람 상세(첫 인연 영역, 빈 타임라인)
- 사람 삭제(확인, cascade)
- **완료 기준:** AC-01~08, AC-26, AC-28, AC-33 통과

### 3단계: 관계 기록
- 기록 추가·수정 화면(기본값, 저장 조건, 긴 메모 입력)
- 타임라인(정렬, 첫 인연 시작점, 섹션 헤더)
- 기록 상세, 기록 삭제
- 함께한 사람 선택과 공동 기록 타임라인 표시, 참여자 기준 삭제 규칙
- **완료 기준:** AC-09~17, AC-27, AC-34, AC-35 통과

### 4단계: 태그와 검색
- 태그 입력 컴포넌트와 정규화
- 검색(대상 필드, 일치 규칙, 근거 표시, 빈 결과)
- **완료 기준:** AC-18~24 통과, 기준 데이터 규모에서 8.5절 성능 목표 충족

### 5단계: 안정성·접근성·실기기 검증
- 저장 실패 경로, 강제 종료 후 재실행 확인
- Dynamic Type, VoiceOver, 다크 모드 점검
- 실기기 2주 사용 후 1.4절 성공 기준 평가
- **완료 기준:** AC-25, AC-29~32 통과, 사용 중 발견한 결함 목록 정리

### 6단계(P1): 후속 개선
- 사용 결과에 따라 FR-012~046 중 우선순위를 다시 정해 진행한다. 초기 후보: 마지막 기록일(FR-040), 이인 지표(FR-044), 전체 보기(FR-045), 앱 잠금(FR-029), 백업(FR-018), 사진(FR-012).

### 11.2 UI 테스트 (XCUITest)

> 아직 UI 테스트 타깃(`SlowConnectionUITests`)이 없다. 지금은 CI 스크린샷(실행 인자로 화면을 바로 열기) · 화소 검사 · CPU 검사와 실기기 확인 목록이 이 자리를 맡는다.

- 시나리오 A(등록), B(기록 추가), C(검색), D(수정·삭제)를 자동화한다.
- 앱 재실행 후 데이터 유지 확인을 포함한다.

### 11.3 수동 테스트 (실기기)

- 접근성: 최대 글자 크기, VoiceOver, 다크 모드
- 긴 메모(20,000자) 입력·저장·읽기
- 기준 데이터 규모(사람 1,000명, 기록 10,000건)를 생성하는 디버그 메뉴로 성능 확인
- 저장 공간 부족 상황은 재현이 어려우므로 실패 저장소 주입으로 대체한다

### 11.4 테스트 데이터

- 디버그 빌드에만 "샘플 데이터 생성"과 "전체 삭제" 메뉴를 둔다. 릴리스 빌드에는 포함하지 않는다.

## 12. 향후 확장 방향

### 12.1 느린 시리즈 연결

- **느린 나이테:** 사람과 업무 과제·프로젝트·성과를 연결
- **느린 커리어:** 함께 수행한 프로젝트와 경험을 경력 기록으로 활용
- **느린 여백:** 회의 메모, 회고, 관련 Markdown 문서 연결
- **느린 가족:** 가족 구성원과 개인 관계 기록을 필요한 범위에서 연결

이 연결은 초기 버전의 필수 조건이 아니다. 먼저 독립 앱으로 핵심 사용성을 검증한 뒤 진행한다. 연결 방식은 6.5절의 `ExternalReference` 확장 지점을 기준으로 설계한다.

### 12.2 추가 기능 후보 (FR 표에 없는 항목)

- 프로젝트별 함께한 사람 보기(FR-016 이후)
- 기록에 사진·파일 첨부
- 위젯·단축어로 빠른 기록 추가
- 연간 돌아보기(올해 새로 만난 사람, 가장 자주 기록한 사람)

후속 연락 리마인더(FR-039)는 사용자의 명시적 선택을 기반으로 하며, 자동 메시지 발송은 기본 동작으로 삼지 않는다.

## 13. 핵심 제품 원칙

느린 인연은 사람을 평가하거나 네트워크를 점수화하는 앱이 아니다. 관계를 더 많이 만드는 것보다 **이미 맺은 인연을 잊지 않고, 함께한 경험의 맥락을 이해하며, 시간이 지난 뒤에도 다시 돌아볼 수 있도록 돕는 것**을 우선한다.

초기 제품의 성공 기준은 기능의 개수가 아니라 다음 질문에 답할 수 있는지에 있다.

> **"이 사람을 어떻게 알게 되었고, 우리는 어떤 시간을 함께했는가?"**

따라서 첫 번째 목표는 복잡한 CRM을 만드는 것이 아니라, **사람 한 명을 등록하고 그 사람과의 인연을 하나 기록하는 경험을 간단하고 안정적으로 제공하는 것**이다.

관계 지표(5.5절)는 이 원칙 안에서만 제공한다. 지표가 답하는 질문은 "이 사람이 얼마나 중요한가"가 아니라 **"내가 이 인연을 어떻게 돌보고 있는가, 내 인연 전체는 어떤 모양인가"** 이다. 사람에게 종합 점수를 매기거나 순위를 세우는 기능은 두지 않으며, 모든 지표는 근거 기록으로 되돌아갈 수 있어야 하고 사용자가 기록한 범위만 반영한다는 사실을 함께 보여 준다.
